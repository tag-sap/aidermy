# Evaluation v2 — новая архитектура оценки (черновик реализации)

Статус: **этап 1 реализации**. Код изолирован в `backend/app/evaluation/`, не подключён
к production-эндпоинтам, миграции не применены. Ветка `feat/evaluation-v2` (от `origin/main`).

## 1. Что оценивается

Оценка строится **по параметрам анкеты**, а не по агрегированным «осям» старого движка.
Реестр параметров — `evaluation/parameters.py`; у каждого параметра: `id`, название,
определение, якоря шкалы 0/50/100 и направление (`benefit` — больше лучше,
`risk` — больше значит меньше риска).

| Параметр | Что означает оценка 100 |
|---|---|
| `hydration` | подтверждённые влагоудерживающие/смягчающие компоненты в значимых позициях |
| `barrier` | подтверждённые барьерные компоненты, нет агрессивных ПАВ |
| `irritation` | подтверждённых раздражителей в значимых позициях не найдено |
| `sensitization` | подтверждённых аллергенов/сенсибилизаторов не найдено |
| `sebum` | подтверждённые себорегулирующие компоненты |
| `comedogenicity` | подтверждённых комедогенных компонентов не найдено |
| `pigmentation` | подтверждённые компоненты, нет фотосенсибилизаторов |
| `texture` | подтверждённые кератолитические механизмы |
| `ageing` | подтверждённые компоненты с описанным механизмом |
| `therapy_safety` | нет конфликта с активной терапией |
| `procedure_safety` | нет факторов риска после процедуры |
| `fragrance_allergen` | подтверждённых ароматизаторов/аллергенов не найдено |

100 — **не** «продукт эффективен» и не вероятность: это соответствие определению
параметра по имеющимся доказательствам.

## 2. Откуда берётся релевантность (веса)

Веса не назначаются вручную для красоты результата — они выводятся из ответов анкеты:

- каждый ID ответа отображается в набор параметров с релевантностью 0…1
  (`ID_RELEVANCE`, `CATEGORY_RELEVANCE`);
- агрегация нескольких ответов — **max**, а не сумма: дополнительные опции не
  увеличивают вес;
- активная терапия учитывается только при `active=true`, процедуры — только «свежие»
  (`<7 / 7–14 / 14–30 дней`);
- аллергии без конкретного аллергена дают параметр `fragrance_allergen` и оговорку
  в ограничениях;
- ответы, не влияющие на оценку в этой версии методики, перечисляются в ограничениях.

Релевантность — проектное решение маппинга анкеты, а не калиброванный вес.
Её изменение = новая версия методики (`method_version`).

## 3. Score Engine (арифметическое среднее с порогом полноты)

`evaluation/engine.py::evaluate(profile, evaluations, rules)` — чистая функция.

1. Релевантность из анкеты определяет **только набор** параметров, которые важны
   пользователю. Весов важности нет: каждому релевантному параметру даётся равная доля.
2. Для каждого параметра берётся **одна** актуальная оценка (`assert_unique`).
3. Оценка включается, только если `status=evaluated`, значение 0…100 и уверенность
   не ниже `min_confidence`.
4. `completeness` = доля включённых параметров среди релевантных.
5. `completeness < threshold` → `total = None`, вердикт не выводится.
6. Иначе `total = (Σ v) / N` — обычное арифметическое среднее доступных значений.
   Пропуски не заменяются нулём и не тянут балл вниз.
7. `verdict` вычисляется только если `rules.calibrated = True`; сейчас это не так.

Гарантии: одинаковый вход + та же версия правил → тот же результат и `input_hash`;
нет скрытых штрафов, блокировок и коэффициентов; отсутствующая оценка **никогда**
не превращается в 0/50/«нейтрально».

Текущие правила — `2.0.0-draft`: `aggregation = arithmetic_mean`,
`completeness_threshold = 0.5`, `calibrated = false`. Предыдущая версия
`1.0.0-draft` (взвешенное среднее) оставлена только для воспроизводимости старых
экспериментов.

## 4. Недостаток данных

| Ситуация | Поведение |
|---|---|
| оценки нет | `status=not_researched`, параметр не включён, полнота падает |
| доказательств недостаточно | `insufficient_evidence`, причина в результате и ограничениях |
| источники противоречат | значение считается по балансу доказательств, в ограничениях явная пометка |
| состав/методика изменились, истёк срок | `stale` (см. `freshness.py`) |
| полнота ниже порога | общий балл не рассчитывается, показываются параметры и причины |
## 5. Актуальность и повторное использование

`evaluation/freshness.py`:

- `composition_hash` — оценка действительна только для той версии состава;
- `method_version` — изменение методики инвалидирует старые оценки;
- `valid_until` и `max_age_days` — срок годности;
- `superseded_by` (в БД) — история не удаляется, актуальной считается одна строка.

Следствие: при наличии актуальной оценки AI не вызывается; исследование запускается
только для отсутствующих/устаревших пар «продукт × параметр».

## 6. Snapshot результата

`evaluation/snapshot.py::build_snapshot` фиксирует: продукт, `composition.hash`,
`profile_fingerprint` (без персональных данных — только ID сигналов и счётчики
аллергий/непереносимостей), параметры со значениями/статусами/весами/причинами,
`total`, `verdict`, `completeness`, `limitations`, версии и хэши, `snapshot_hash`
и `snapshot_id`.

`verify_snapshot` обнаруживает любое изменение сохранённого результата. UI и отчёт
должны читать только snapshot — пересчёт в отчёте запрещён.

`snapshot_id` вычисляется по **входам** (продукт, версия состава, fingerprint профиля,
параметры, версии правил/движка, `user_id`) и не зависит от времени создания: повторный
запрос с теми же данными возвращает тот же snapshot. `created_at` входит только в
`snapshot_hash`, поэтому первый сохранённый результат не перезаписывается.

## 7. Схема БД (черновик)

`backend/migrations/20261023_evaluation_v2.sql` — схема `evaluation`:
`product_compositions`, `parameter_registry`, `research_jobs`, `sources`, `evidence`,
`parameter_evaluations`, `rule_versions`, `snapshots` (+ `product_name` в snapshot,
чтобы UI не делал join к каталогу). RLS включён; snapshot — append-only (триггер);
уникальные индексы защищают от дублей AI-задач и повторных snapshot с теми же входами.
**Миграция не применена.**

## 7.1. Хранилище

- `store.py::EvaluationStore` — протокол; `InMemoryStore` — эталонная реализация для тестов.
- `postgres_store.py::PostgresStore` — реализация поверх `evaluation.*`:
  - все запросы параметризованы;
  - `save_evaluation` выполняется в транзакции: `SELECT ... FOR UPDATE` → `INSERT` →
    `UPDATE ... SET superseded_by` (история сохраняется);
  - `save_snapshot` идемпотентен по `snapshot_id` (`ON CONFLICT DO NOTHING`),
    требует зарегистрированного `rule_version` и `composition` (иначе `StoreError`);
  - `enqueue_research` опирается на частичный уникальный индекс — дубли AI-задач
    не создаются;
  - `seed_rule()` / `seed_registry()` регистрируют версию правил и реестр параметров.

Запуск:

```bash

  python -m pytest tests/test_evaluation_postgres_integration.py -q
# 31 passed
```

Схема пересоздаётся из файла миграции при каждом прогоне (`drop schema … cascade`
+ apply), поэтому тест проверяет **текущую** миграцию, а не остатки прошлой.
Supabase-специфичные объекты эмулируются явно: схема `auth`, `auth.uid()` от
`request.jwt.claim.sub`, роли `anon` / `authenticated` / `service_role`
(последняя с `BYPASSRLS`), поскольку миграция ссылается на `auth.uid()`.

Покрытие (31 проверка):

- полный цикл `seed_rule → ensure_composition → save_evaluation → build → read → verify`;
- повторные запросы: повторный `build` возвращает тот же snapshot (`reused=True`, 1 строка);
- `ON CONFLICT`: upsert состава, `snapshots DO NOTHING`, дедуп research-задач;
- транзакции и rollback: принудительный откат не оставляет «половинчатого» supersede;
- ограничения: value 0–100, `evaluated` требует value, confidence 0–1, допустимые статусы;
- внешние ключи: несуществующий `composition_id` и незарегистрированный `rule_version`;
- `jsonb`: кавычки, переводы строк, табуляция, emoji, обратный слеш, `{json}`;
- даты: `valid_until` (актуально/просрочено), `evaluated_at` из БД;
- конкурентность: два потока `save_evaluation` и два потока `build`;
- история supersede: 2 версии, одна текущая, `superseded_by` указывает на новую;
- неизменяемость snapshot: `UPDATE`/`DELETE` блокируются триггером; при отключённом
  триггере подмена обнаруживается `verify_snapshot`;
- миграция идемпотентна (повторное применение).

RLS проверен **реальными ролями** (не «на слово»):

| Проверка | Результат |
|---|---|
| `authenticated` без GRANT | `InsufficientPrivilege` (доступ закрыт по умолчанию) |
| `authenticated` + `GRANT SELECT`, claim sub=1 | видит ровно 1 свою строку |
| claim sub=2 и запрос чужого `snapshot_id` | 0 строк |
| `authenticated` + `GRANT INSERT` | `InsufficientPrivilege` (нет INSERT-политики) |
| `anon` | `InsufficientPrivilege` |
| `service_role` (BYPASSRLS) | видит обе строки |

Найденные реальной БД дефекты (исправлены):

1. **`snapshot` не сериализовался**: `composition.verified_at` из Postgres — `datetime`,
   а не строка → `TypeError`. Добавлена нормализация `_iso()`; без неё прод-путь
   через БД падал бы на первом же расчёте.
2. **Гонка при первой записи оценки**: `SELECT … FOR UPDATE` не блокирует ещё не
   существующую строку → второй поток получал `UniqueViolation`. Добавлен
   `pg_advisory_xact_lock` по естественному ключу.
3. **Порядок supersede**: частичный уникальный индекс запрещает две текущие строки
   даже внутри транзакции, поэтому «вставить → обновить» падало. Теперь
   «обновить старое → вставить новое», а FK `superseded_by` сделан
   `deferrable initially deferred`.

Ограничения этой проверки:

- локальный кластер, не Supabase: не проверены TLS, пулер соединений, права
  Supabase-роли `postgres` и поведение `auth.uid()` с реальным JWT;
- `service_role` эмулирован флагом `BYPASSRLS`, а не платформой Supabase;
- один поток/процесс-хост: конкурентность проверена потоками, но не распределённо;
- Storage/S3 не участвует в этих тестах.

## 12. AI-слой исследования (доказательства)

### 12.1 Контракт доказательства (`evaluation/evidence.py`)

Доказательство — типизированная запись, а не текст модели:

| Поле | Смысл |
|---|---|
| `parameter_id` | параметр, к которому относится утверждение |
| `claim` | проверяемое утверждение (что именно утверждается) |
| `quote` | дословная цитата из источника |
| `source` | URL (http/https), заголовок, издатель, тип, дата получения, hash содержимого |
| `product_id`, `composition_hash` | привязка к продукту и **версии состава** |
| `direction` | `supports` / `contradicts` / `neutral` |
| `strength` | `weak` / `moderate` / `strong` |
| `confidence` | 0…1, уверенность извлечения |
| `extraction_method` | как извлечено (версия метода) |
| `verification` | `confirmed` / `unverified` / `rejected` (+ `rejection_reason`) |
| `retrieved_at` | когда источник получен |

Правила валидации (`validate_candidate`):

1. `parameter_id` кандидата обязан совпадать с параметром запроса;
2. цитата не пустая, ≥ 8 значимых символов;
3. обязателен `source_text` (текст источника) — без него цитату проверить нельзя;
4. нормализованная цитата (регистр/пунктуация/пробелы) должна **дословно** встречаться
   в тексте источника — иначе `rejected`;
5. дата получения обязательна, корректна и не в будущем;
6. привязка к продукту/составу берётся **из запроса**, а не из ответа модели.

Отклонённые кандидаты сохраняются для аудита, но никогда не участвуют в оценке.
Отсутствие доказательств пользы даёт `insufficient_evidence`, а **не** низкий балл:
«нет данных о пользе» ≠ «доказан вред».

### 12.2 Провайдер (`evaluation/research.py`)

```python
class ResearchProvider(Protocol):
    name: str
    def research(self, request: ResearchRequest) -> ResearchOutcome: ...
```

`ResearchRequest` содержит продукт, версию состава, INCI, параметр, его определение
и якоря шкалы. `ResearchOutcome` имеет статус `ok | insufficient_evidence |
source_unavailable | provider_error`, кандидатов, текст ошибки, токены и стоимость.

`FakeResearchProvider` — детерминированная реализация для тестов: отвечает по
`parameter_id` (или `(product, composition, parameter)`), ведёт журнал вызовов и
суммарную стоимость. **Реальные сетевые вызовы не выполняются.**

### 12.3 Оркестрация (`evaluation/research_service.py`)

```
plan → needed = релевантные параметры без актуальной оценки
     → enqueue_research (дедуп по активной задаче)
     → claim_job (FOR UPDATE SKIP LOCKED)
     → provider.research
     → validate_candidates → save_evidence
     → assess (детерминированные полосы) → save_evaluation
     → complete_job / fail_job
```

- **Повторное использование**: если для (состав, параметр, метод) есть актуальная
  оценка — провайдер не вызывается вообще.
- **Устаревание**: смена `composition_hash`, `method_version`, `valid_until` или
  превышение `max_age_days` возвращает параметр в план исследования.
- **Дедупликация**: частичный уникальный индекс `uq_research_jobs_active` плюс
  проверка активной задачи — два параллельных запроса создают одну задачу.
- **Конкурентность**: `claim_job` помечает задачу `processing` и увеличивает `attempts`;
  второй воркер получает следующую задачу или ничего.
- **Ошибки**: `provider_error`, `source_unavailable`, исключение провайдера и
  «все кандидаты отклонены» → задача `failed` с причиной; оценка не создаётся,
  статус успеха не выставляется.
- **Повторы**: не более `max_attempts` (по умолчанию 3), затем параметр попадает в
  `exhausted` и больше не запускается автоматически.
- **Стоимость**: лимит на задачу (`max_cost_per_job`) и на прогон
  (`max_cost_per_run`); при исчерпании бюджета прогон останавливается, задачи
  возвращаются в `pending` (`deferred`), токены и стоимость пишутся в задачу.

### 12.4 Из доказательств в значение (`evaluation/assessment.py`)

Модель **не выбирает число**. Значение выводится детерминированно:

```
weight(evidence) = strength_weight × confidence      # weak .3 / moderate .6 / strong 1.0
net = (Σ supports − Σ contradicts) / (Σ supports + Σ contradicts + 0.6)
```

`0.6` — «прежнее незнание»: без него одна слабая цитата выглядела бы так же
убедительно, как сильная. Полосы: `net ≥ .6 → 80`, `≥ .3 → 70`, `> 0 → 60`,
`|net| ≤ .05 при наличии обеих сторон → 50` (баланс), `< 0 → 40`, `≤ −.3 → 30`,
`≤ −.6 → 20`. Правило версионировано (`evidence-bands-1.0.0`) и **не откалибровано**;
это прямо написано в ограничениях каждой оценки.

`rationale` собирается только из подтверждённых `claim` + `quote` + домена источника.
Отклонённые утверждения в текст не попадают — только их количество и причины.

### 12.5 Хранение

`evaluation.sources` (URL + content_hash уникальны) и `evaluation.evidence`
(привязка к `composition_id` и `parameter_id`, уникальность
`(composition_id, parameter_id, source_id, md5(quote))`). Задача хранится в
`evaluation.research_jobs` (статусы, попытки, worker, locked_until, токены, стоимость).

### 12.6 Чего в этом этапе нет

**Реального поиска и загрузки источников нет.** Реализован контракт провайдера и
fake-реализация; production-провайдер (веб-поиск + fetch + LLM-извлечение) не
подключён, платные вызовы не выполнялись. Это осознанно незавершённая часть:
без реального поиска нельзя утверждать, что система находит доказательства.
