# Evaluation v2 — новая архитектура оценки (черновик реализации)

Статус: **этап 1 реализации**. Код изолирован в `backend/app/evaluation/`, не подключён
к production-эндпоинтам, миграции не применены. Ветка `feat/evaluation-v2` (от `origin/main`).

## 1. Что оценивается

Оценка строится **по реальным подпараметрам анкеты**, которые выбрал пользователь,
а не по универсальному набору «характеристик продукта».

Источник параметров — `evaluation/questionnaire.py`. Идентификаторы и подписи скопированы
из production-анкеты (`figma-make-preview/src/data.ts`), а тест
`tests/test_evaluation_questionnaire.py` **парсит этот TS-файл** и падает, если каталог
разошёлся с анкетой (новый/переименованный/удалённый вариант).

| Раздел анкеты | Поле payload | Параметр оценки | Пример |
|---|---|---|---|
| Тип кожи | `skin_type` | `skin_type:<id>` | `skin_type:dry` |
| Возраст | `age` | **не оценивается** — только контекст | — |
| Проблемы | `concerns` (подписи) / `structured.concerns` (id) | `problem:<card>` | `problem:acne_general` |
| Лечение | `structured.therapy` | `therapy:<вещество>` | `therapy:tretinoin` |
| Процедуры | `structured.procedures` | `procedure:<процедура>@<период>` | `procedure:recent_laser@<7` |
| Непереносимости | `allergies` / `structured.intolerances` | `intolerance:<категория>` | `intolerance:fragrance_intolerance` |
| Цели | `goals` / `structured.goals` | `goal:<id>` | `goal:hydration` |

Каждый параметр несёт:

- `label` — как пункт называется для пользователя («Проблема: «Сухость / обезвоженность»»);
- `question` — вопрос, на который отвечает оценка («Соответствует ли состав задаче «…»?»);
- `definition` — что именно искать в источниках (включая технические подсказки
  `product_axes`: себорегуляция, комедогенность, фотосенсибилизация и т.п.);
- якоря 0/50/100 и направление (`benefit` / `risk`).

Технические характеристики продукта (`product_axes`) **не являются** единицами хранения
результата: они лишь описывают, что искать внутри пользовательского подпараметра.

Решения, зафиксированные явно:

- **возраст** не создаёт параметр: возраст сам по себе не является свойством продукта,
  а знание о продукте должно быть одинаковым для всех пользователей;
- **ветки уточнений** проблемы («папулы», «шелушение») — уточнения карточки, а не
  отдельные оценки; иначе один и тот же продукт исследовался бы заново под каждый набор
  симптомов, а результат нельзя было бы переиспользовать;
- **период после процедуры** входит в идентичность параметра: «лазер, <7 дней» и
  «лазер, 7–14 дней» — разные вопросы; `>3m` ограничений не создаёт (проектное решение);
- **непереносимость конкретного ингредиента** из структурированного профиля получает
  собственный параметр `intolerance:ingredient:<name>`.

100 — **не** «продукт эффективен» и не вероятность: это соответствие требованию
конкретного пункта анкеты по подтверждённым доказательствам.

## 2. Откуда берётся набор параметров

Релевантность — это не вес, а **состав набора**: какие сохранённые оценки нужны
конкретному профилю (`parameters.resolve_parameters`).

- ответы принимаются и как id, и как подписи (production-фронтенд присылает подписи:
  `concerns: ["Высыпания"]`, `allergies: ["Отдушки"]`);
- активная терапия учитывается только при `active=true`; конкретное вещество важнее группы
  (`therapy:tretinoin`, а не `therapy:topical_retinoid`);
- несопоставленные ответы **не угадываются**: они перечисляются в `notes`/`unresolved`
  и попадают в ограничения результата;
- `skin_goals` (устаревшие названия измерений) автоматически не маппятся — об этом
  пишется оговорка.

Изменение этого маппинга = новая версия методики (`method_version`).

## 3. Score Engine (только `assessed`, обычное среднее)

`evaluation/engine.py::evaluate(profile, evaluations, rules)` — чистая функция.

1. Анкета определяет **только набор** параметров, которые важны пользователю.
   Весов важности нет: каждому параметру даётся равная доля.
2. Для каждого параметра берётся **одна** актуальная оценка (`assert_unique`).
3. В среднее входит **только** `status=assessed` (балл 0/25/50/75/100 + объяснение +
   ссылки на подтверждённые доказательства).
4. `pending`, `not_applicable`, `insufficient_evidence`, `stale` и legacy-строки
   исключаются; их значения не подставляются.
5. `total = Σ(assessed_scores) / count(assessed_scores)` — без порога покрытия,
   без весов, без штрафов, без «оценки доказанности».
6. Если нет ни одной `assessed`, `total = None` и в ограничениях прямо сказано,
   что итоговая совместимость не определена.
7. Итог может быть дробным (например `58.33`): округляется только само среднее
   (2 знака для отображения), баллы подпараметров не меняются.
8. `verdict` вычисляется только если `rules.calibrated = True`; сейчас это не так.

Гарантии: одинаковый вход + та же версия правил → тот же результат и `input_hash`;
отсутствующая оценка **никогда** не превращается в 0/50/«нейтрально».

Текущие правила — `3.0.0-draft`: `aggregation = arithmetic_mean`,
`completeness_threshold = 0` (порог отключён), `score_levels = [0,25,50,75,100]`,
`calibrated = false`. `2.0.0-draft` (полосы доказательств) и `1.0.0-draft`
(взвешенное среднее) оставлены только для воспроизводимости старых экспериментов;
их результаты не переносятся в новую методику как авторитетные.

Единые критерии уровней (`contracts.SCORE_LEVEL_CRITERIA`, отдаются в
`GET /parameters` → `score_criteria`):

| Балл | Критерий |
|---|---|
| 0 | подтверждённые данные прямо противоречат требованию пользователя |
| 25 | в основном не соответствуют, есть отдельные совпадения |
| 50 | частично соответствуют и частично противоречат; выбран осознанно и обоснован, **не** «неизвестно» |
| 75 | в основном соответствуют, есть второстепенные ограничения |
| 100 | прямо соответствуют, существенных возражений нет |

Формулировки предварительные: они описывают соответствие требованию пункта, а не
клиническую эффективность, и не откалиброваны по эталонной выборке.

## 4. Статусы результата и недостаток данных

| Статус | Значение | Балл | В среднем |
|---|---|---|---|
| `pending` | параметр ещё не исследован | нет | нет |
| `assessed` | допустимый балл + объяснение + доказательства | 0/25/50/75/100 | **да** |
| `not_applicable` | параметр неприменим к продукту (с обоснованием и источником) | нет | нет |
| `insufficient_evidence` | применим, но доказательств недостаточно | нет | нет |
| `stale` | оценка относится к другому составу/методике | нет | нет |
| `evaluated`, `not_researched`, `contradictory_evidence` | legacy-строки ранних черновиков | только для аудита | нет |

Инварианты:

- только `assessed` содержит балл; остальные статусы — без числа;
- `assessed` невозможен без объяснения и ссылок на сохранённые подтверждённые
  доказательства (проверяется и в коде, и в БД);
- `not_applicable` — это не «исследование не удалось», а обоснованный вывод о
  продукте; без подтверждённого источника такой статус не принимается;
- `insufficient_evidence` — не отрицательная совместимость;
- техническая ошибка провайдера/валидации — это `failed` задача, а не статус
  результата; задача остаётся доступной для повторной попытки.
## 5. Актуальность и повторное использование

`evaluation/freshness.py`:

- `composition_hash` — оценка действительна только для той версии состава;
- `method_version` — изменение методики инвалидирует старые оценки;
- `valid_until` и `max_age_days` — срок годности;
- `superseded_by` (в БД) — история не удаляется, актуальной считается одна строка.

Следствие: при наличии актуальной оценки AI не вызывается; исследование запускается
только для отсутствующих/устаревших пар «продукт × параметр».

## 6. Snapshot результата

`evaluation/snapshot.py::build_snapshot` фиксирует: продукт, `composition.hash`,
`composition.source`, `composition.verified_at`, **`composition.status`**,
`profile_fingerprint` (без персональных данных: тип кожи, возраст, проблемы,
терапия, процедуры, цели; непереносимости — только счётчиком), **только оценённые**
параметры (`status=assessed`) со значениями и объяснениями, `total`, `verdict`,
`completeness` (внутренняя диагностика), `limitations`, версии и хэши,
`snapshot_hash` и `snapshot_id`.

`pending`, `not_applicable` и `insufficient_evidence` **не попадают** в список
оценённых параметров и не влияют на среднее, но сохраняются в
`evaluation.parameter_evaluations` (история и статусы не удаляются).

Если состав не `active`, в `limitations` добавляется предупреждение, что результат
справочный; `status` входит в `snapshot_id`, поэтому проверка состава создаёт новый
snapshot, а старый не перезаписывается. `completeness` остаётся внутренней
диагностикой (доля оценённых), не входит в балл и не является показателем качества.

`verify_snapshot` обнаруживает любое изменение сохранённого результата. UI и отчёт
должны читать только snapshot — пересчёт в отчёте запрещён.

`snapshot_id` вычисляется по **входам** (продукт, версия состава, fingerprint профиля,
параметры, версии правил/движка, `user_id`) и не зависит от времени создания: повторный
запрос с теми же данными возвращает тот же snapshot. `created_at` входит только в
`snapshot_hash`, поэтому первый сохранённый результат не перезаписывается.

## 7. Схема БД (черновик)

`backend/migrations/20261023_evaluation_v2.sql` — схема `evaluation`:
`product_compositions`, `parameter_registry`, `research_jobs`, `sources`, `evidence`,
`parameter_evaluations`, `rule_versions`, `snapshots` (+ `product_name` в snapshot,
чтобы UI не делал join к каталогу). RLS включён; snapshot — append-only (триггер);
уникальные индексы защищают от дублей AI-задач и повторных snapshot с теми же входами.
**Миграция не применена.**

## 7.1. Хранилище

- `store.py::EvaluationStore` — протокол; `InMemoryStore` — эталонная реализация для тестов.
- `postgres_store.py::PostgresStore` — реализация поверх `evaluation.*`:
  - все запросы параметризованы;
  - `save_evaluation` выполняется в транзакции: `SELECT ... FOR UPDATE` → `INSERT` →
    `UPDATE ... SET superseded_by` (история сохраняется);
  - `save_snapshot` идемпотентен по `snapshot_id` (`ON CONFLICT DO NOTHING`),
    требует зарегистрированного `rule_version` и `composition` (иначе `StoreError`);
  - `enqueue_research` опирается на частичный уникальный индекс — дубли AI-задач
    не создаются;
  - `seed_rule()` / `seed_registry()` регистрируют версию правил и реестр параметров.

## 7.2. API (`/api/v1/evaluation`)

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| GET | `/parameters` | публично | каталог анкеты (разделы, варианты, периоды) + реестр параметров + описание правил (`calibrated: false`) |
| POST | `/preview` | публично | чистый расчёт без сохранения (для проверки методики) |
| POST | `/snapshots` | авторизация | собрать/переиспользовать snapshot, вернуть `pending_parameters` |
| GET | `/snapshots/{id}` | владелец | чтение snapshot с проверкой целостности |
| POST | `/research-jobs` | авторизация | поставить в очередь только отсутствующие параметры; `409`, если состав не подтверждён |

Роутер **не зарегистрирован** в `app/main.py`: включение — одна строка
`setup_evaluation_routes(app, store=PostgresStore())` после применения миграции.

## 10. Интеграционная проверка на реальном PostgreSQL

Проведена 2026-10-23 на **изолированном локальном** PostgreSQL, а не на Supabase.

| Параметр | Значение |
|---|---|
| Сервер | PostgreSQL 16.2 (автономный кластер `pgserver`, без прав администратора) |
| Адрес | `127.0.0.1:57879` |
| База | `aidermy_eval_test` (создана специально для теста) |
| Пользователь | `postgres` (локальный, trust-auth, пароль не используется/не печатается) |
| SSL | выключен (локально); в Supabase обязателен TLS — это различие зафиксировано |
| Production | **не использовался**: guard отклоняет `*.supabase.*`, IP сервера, `eclectusgames.ru`, любой не-localhost и любую БД вне `aidermy_eval_test*` |

Запуск:

```bash
EVALUATION_TEST_DSN="postgresql://…@127.0.0.1:57879/aidermy_eval_test" \
  python -m pytest tests/test_evaluation_postgres_integration.py -q
# 31 passed
```

Схема пересоздаётся из файла миграции при каждом прогоне (`drop schema … cascade`
+ apply), поэтому тест проверяет **текущую** миграцию, а не остатки прошлой.
Supabase-специфичные объекты эмулируются явно: схема `auth`, `auth.uid()` от
`request.jwt.claim.sub`, роли `anon` / `authenticated` / `service_role`
(последняя с `BYPASSRLS`), поскольку миграция ссылается на `auth.uid()`.

Покрытие (31 проверка):

- полный цикл `seed_rule → ensure_composition → save_evaluation → build → read → verify`;
- повторные запросы: повторный `build` возвращает тот же snapshot (`reused=True`, 1 строка);
- `ON CONFLICT`: upsert состава, `snapshots DO NOTHING`, дедуп research-задач;
- транзакции и rollback: принудительный откат не оставляет «половинчатого» supersede;
- ограничения: value 0–100, `evaluated` требует value, confidence 0–1, допустимые статусы;
- внешние ключи: несуществующий `composition_id` и незарегистрированный `rule_version`;
- `jsonb`: кавычки, переводы строк, табуляция, emoji, обратный слеш, `{json}`;
- даты: `valid_until` (актуально/просрочено), `evaluated_at` из БД;
- конкурентность: два потока `save_evaluation` и два потока `build`;
- история supersede: 2 версии, одна текущая, `superseded_by` указывает на новую;
- неизменяемость snapshot: `UPDATE`/`DELETE` блокируются триггером; при отключённом
  триггере подмена обнаруживается `verify_snapshot`;
- миграция идемпотентна (повторное применение).

RLS проверен **реальными ролями** (не «на слово»):

| Проверка | Результат |
|---|---|
| `authenticated` без GRANT | `InsufficientPrivilege` (доступ закрыт по умолчанию) |
| `authenticated` + `GRANT SELECT`, claim sub=1 | видит ровно 1 свою строку |
| claim sub=2 и запрос чужого `snapshot_id` | 0 строк |
| `authenticated` + `GRANT INSERT` | `InsufficientPrivilege` (нет INSERT-политики) |
| `anon` | `InsufficientPrivilege` |
| `service_role` (BYPASSRLS) | видит обе строки |

Найденные реальной БД дефекты (исправлены):

1. **`snapshot` не сериализовался**: `composition.verified_at` из Postgres — `datetime`,
   а не строка → `TypeError`. Добавлена нормализация `_iso()`; без неё прод-путь
   через БД падал бы на первом же расчёте.
2. **Гонка при первой записи оценки**: `SELECT … FOR UPDATE` не блокирует ещё не
   существующую строку → второй поток получал `UniqueViolation`. Добавлен
   `pg_advisory_xact_lock` по естественному ключу.
3. **Порядок supersede**: частичный уникальный индекс запрещает две текущие строки
   даже внутри транзакции, поэтому «вставить → обновить» падало. Теперь
   «обновить старое → вставить новое», а FK `superseded_by` сделан
   `deferrable initially deferred`.

Ограничения этой проверки:

- локальный кластер, не Supabase: не проверены TLS, пулер соединений, права
  Supabase-роли `postgres` и поведение `auth.uid()` с реальным JWT;
- `service_role` эмулирован флагом `BYPASSRLS`, а не платформой Supabase;
- один поток/процесс-хост: конкурентность проверена потоками, но не распределённо;
- Storage/S3 не участвует в этих тестах.

## 12. AI-слой исследования (доказательства)

### 12.1 Контракт доказательства (`evaluation/evidence.py`)

Доказательство — типизированная запись, а не текст модели:

| Поле | Смысл |
|---|---|
| `parameter_id` | параметр, к которому относится утверждение |
| `claim` | проверяемое утверждение (что именно утверждается) |
| `quote` | дословная цитата из источника |
| `source` | URL (http/https), заголовок, издатель, тип, дата получения, hash содержимого |
| `product_id`, `composition_hash` | привязка к продукту и **версии состава** |
| `direction` | `supports` / `contradicts` / `neutral` |
| `strength` | `weak` / `moderate` / `strong` |
| `confidence` | 0…1, уверенность извлечения |
| `extraction_method` | как извлечено (версия метода) |
| `verification` | `confirmed` / `unverified` / `rejected` (+ `rejection_reason`) |
| `retrieved_at` | когда источник получен |

Правила валидации (`validate_candidate`):

1. `parameter_id` кандидата обязан совпадать с параметром запроса;
2. цитата не пустая, ≥ 8 значимых символов;
3. обязателен `source_text` (текст источника) — без него цитату проверить нельзя;
4. нормализованная цитата (регистр/пунктуация/пробелы) должна **дословно** встречаться
   в тексте источника — иначе `rejected`;
5. дата получения обязательна, корректна и не в будущем;
6. привязка к продукту/составу берётся **из запроса**, а не из ответа модели.

Отклонённые кандидаты сохраняются для аудита, но никогда не участвуют в оценке.
Отсутствие доказательств пользы даёт `insufficient_evidence`, а **не** низкий балл:
«нет данных о пользе» ≠ «доказан вред».

### 12.2 Провайдер (`evaluation/research.py`)

```python
class ResearchProvider(Protocol):
    name: str
    def research(self, request: ResearchRequest) -> ResearchOutcome: ...
```

`ResearchRequest` содержит продукт, версию состава, INCI, параметр, его определение
и якоря шкалы. `ResearchOutcome` имеет статус `ok | insufficient_evidence |
source_unavailable | provider_error`, кандидатов, текст ошибки, токены и стоимость.

`FakeResearchProvider` — детерминированная реализация для тестов: отвечает по
`parameter_id` (или `(product, composition, parameter)`), ведёт журнал вызовов и
суммарную стоимость. **Реальные сетевые вызовы не выполняются.**

### 12.3 Оркестрация (`evaluation/research_service.py`)

```
plan → needed = релевантные параметры без актуальной оценки
     → enqueue_research (дедуп по активной задаче)
     → claim_job (FOR UPDATE SKIP LOCKED)
     → provider.research
     → validate_candidates → save_evidence
     → assess (валидация предложения модели) → save_evaluation
     → complete_job / fail_job
```

- **Повторное использование**: если для (состав, параметр, метод) есть актуальная
  оценка — провайдер не вызывается вообще.
- **Устаревание**: смена `composition_hash`, `method_version`, `valid_until` или
  превышение `max_age_days` возвращает параметр в план исследования.
- **Дедупликация**: частичный уникальный индекс `uq_research_jobs_active` плюс
  проверка активной задачи — два параллельных запроса создают одну задачу.
- **Конкурентность**: `claim_job` помечает задачу `processing` и увеличивает `attempts`;
  второй воркер получает следующую задачу или ничего.
- **Ошибки**: `provider_error`, `source_unavailable`, исключение провайдера и
  «все кандидаты отклонены» → задача `failed` с причиной; оценка не создаётся,
  статус успеха не выставляется.
- **Повторы**: не более `max_attempts` (по умолчанию 3), затем параметр попадает в
  `exhausted` и больше не запускается автоматически.
- **Стоимость**: лимит на задачу (`max_cost_per_job`) и на прогон
  (`max_cost_per_run`); при исчерпании бюджета прогон останавливается, задачи
  возвращаются в `pending` (`deferred`), токены и стоимость пишутся в задачу.

### 12.4 Оценка и проверка результата (`evaluation/assessment.py`)

Модель исследования **сама выбирает балл** из пяти уровней и принимает два отдельных
решения: применим ли параметр и достаточно ли доказательств. Детерминированная часть
не выводит совместимость из цитат и не считает их количество:

```
proposal = {
  parameter_id, applicability: applicable|not_applicable, applicability_reason,
  sufficient: bool, score: 0|25|50|75|100|null,
  rationale, limitations[], contradictions[], important_unknowns[],
  evidence_refs[]           # ссылки на кандидатов, сохранённых как evidence
}
```

Что проверяется детерминированно:

1. `parameter_id` совпадает с исследуемым пунктом;
2. `applicability` — только `applicable` / `not_applicable`;
3. ссылки на доказательства существуют, не выходят за диапазон и указывают на
   **подтверждённые** записи (отклонённые цитаты не могут обосновать балл);
4. если `sufficient = true`, балл обязателен и входит в `0/25/50/75/100`;
5. если балл есть, обязательны объяснение (≥ 30 символов), ссылки на подтверждённые
   доказательства и отсутствие клинических утверждений («лечит», «гарантирует»,
   «безопасен»);
6. `sufficient = false` не может содержать балл; балл не может быть «50 по
   умолчанию», если объяснение говорит «данных нет»;
7. `not_applicable` требует обоснования **и** подтверждённого источника. Если
   источника нет, статус понижается до `insufficient_evidence`: неприменимость
   нельзя выводить из отсутствия информации. Для параметров безопасности
   (`intolerance`, `therapy`, `procedure`) неприменимость отклоняется всегда.

Объяснение (`rationale`) = название и вопрос пункта + ответ модели + дословные цитаты
подтверждённых источников + оговорка о том, что выводы сверх цитат не делаются.
Никакого второго вызова ИИ для объяснения нет.

Чего эта проверка **не** делает: она не доказывает косметологическую корректность
вывода модели и не проверяет, что `source_text` действительно загружен со страницы.
Это ограничение зафиксировано ниже и в `research.py`.

Формат объяснения:

1. `label` + `question` параметра («Проблема: «Высыпания». Соответствует ли состав
   задаче «Высыпания»?»);
2. ответ модели (её обоснование выбора уровня и решения о достаточности);
3. по каждой подтверждённой цитате: `claim` — «quote» (домен источника);
4. явное указание, что учтены только цитаты, найденные в тексте источника.

Отклонённые утверждения в текст не попадают — только их количество и причины
(в `limitations`). Объяснение не утверждает лечение, безопасность или вред:
клинические формулировки отклоняются валидатором, а «отсутствие пользы» отделено от
«доказанного вреда».

### 12.5 Хранение

`evaluation.sources` (URL + content_hash уникальны) и `evaluation.evidence`
(привязка к `composition_id` и `parameter_id`, уникальность
`(composition_id, parameter_id, source_id, md5(quote))`). Задача хранится в
`evaluation.research_jobs` (статусы, попытки, worker, locked_until, токены, стоимость).

Новые статусы и инварианты закреплены и в БД (`20261024_evaluation_v2_statuses.sql`):
CHECK на `pending/assessed/not_applicable/insufficient_evidence` (+ legacy-значения),
`assessed` требует балл из `0/25/50/75/100`, объяснение и непустой `evidence_ids`;
остальные статусы не могут содержать балл; `snapshots.total` стал `numeric(5,2)`,
чтобы дробное среднее не искажалось. Ограничения добавлены `NOT VALID`, поэтому
старые строки не удаляются и не переписываются.

### 12.6 Чего в этом этапе нет

**Реального поиска и загрузки источников нет.** Реализован контракт провайдера и
fake-реализация; production-провайдер (веб-поиск + fetch + LLM-извлечение) не
подключён, платные вызовы не выполнялись. Это осознанно незавершённая часть:
без реального поиска нельзя утверждать, что система находит доказательства.

### 12.7 Статус состава

Состав создаётся как `unverified`, пока вызывающая сторона не подтвердила его:

- `verified_at` (или явный `status`) при регистрации → `active`;
- иначе `unverified`, и `ResearchService.plan` **не запускает исследование**
  (`blocked=true`, задач нет): неподтверждённый INCI может быть не тем составом;
- `store.verify_composition(composition_id, verified_at, source)` переводит состав в
  `active` после ручной/автоматической проверки;
- `upsert` никогда не понижает `active` обратно в `unverified`;
- snapshot всегда содержит `composition.status`; для не-`active` состава в ограничения
  добавляется «Состав не подтверждён… результат справочный».

Сбой провайдера (`provider_error`, `source_unavailable`, все кандидаты отклонены) задачу
завершает как `failed`, оценку не пишет; повторный запуск создаёт новую попытку, а
уникальный индекс не даёт двум активным задачам существовать одновременно.

### 12.8 Переиспользование между пользователями

Ключ знания — `(product_id, composition_hash, parameter_id, method_version)`.
Профиль пользователя только выбирает, какие ключи нужны; он не входит в сохранённый
результат и не влияет на объяснение. Проверено тестами
`tests/test_evaluation_questionnaire.py`:

- два пользователя с одинаковым подпараметром получают одинаковые `value`,
  `rationale` и `evidence_ids`, провайдер вызывается один раз;
- повторный запрос при актуальной оценке не вызывает провайдер;
- новый подпараметр создаёт отдельную оценку, старые не меняются;
- смена состава делает старые оценки неприменимыми (`needed` = все параметры);
- смена версии методики запускает новое исследование, старые строки остаются историей;
- другой профиль добавляет свои параметры, не перезаписывая чужие доказательства.

Открытые предметные вопросы (решение не принято, поведение изолировано и покрыто тестами):

1. **Критерии пяти уровней.** Шкала `0/25/50/75/100` зафиксирована, но словесные
   критерии каждого уровня ещё не утверждены как методика и не откалиброваны на
   эталонной выборке. Нужно согласовать формулировки (особенно `50` — «частично/
   смешанно», а не «неизвестно») и проверить согласие модели с экспертной разметкой.
2. **Гранулярность проблем.** Сейчас единица знания — карточка проблемы («Высыпания»),
   а ветки («папулы», «пустулы») считаются уточнением. Нужно решить, требуется ли
   отдельная оценка под каждый подтип (дороже в 5–7 раз на продукт).
3. **Клиент не отправляет цели и id непереносимостей.** `App.tsx` собирает `goals`,
   но в `onDone` их нет; непереносимости уходят подписями. Бэкенд принимает
   `goals`/`structured.goals`, но фактический payload их не содержит — нужна правка
   фронтенда (в этой задаче не выполнялась).
4. **Непереносимости и состав.** Наличие отдушки/спирта — свойство самого INCI, его
   надёжнее проверять детерминированно по составу, а не по маркетинговым цитатам.
   Механизм сверки ингредиентов в evaluation-слое не реализован.
5. **Периоды процедур.** `1–3 месяца` оценивается, `>3 месяцев` — нет. Это проектное
   решение, а не медицински подтверждённое правило.
6. **`source_text` от провайдера.** Валидация проверяет, что цитата есть в `source_text`,
   но не доказывает, что `source_text` действительно загружен со страницы. Реальный
   провайдер обязан передавать текст страницы, а не текст модели (зафиксировано в
   docstring `research.py`); проверка хэша содержимого появится вместе с fetcher.
